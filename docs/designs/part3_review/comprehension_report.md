## Paraphrase 1: the feature (lines 1 to 628)

**What this proposes.** Part 3 extends an existing C++23 header-only graph library (a university course project) so that:

* the user chooses at run time whether a graph is directed;
* Bellman-Ford finds every vertex's shortest distance and path to one target, even with negative weights, with two optimizations that can be switched off (stop after a round with no change; relax only from vertices that changed in the last round);
* a separate whole-graph check, run once per graph, finds a negative cycle anywhere, including one-arc cycles from negative self-loops, which the file reader now keeps instead of dropping;
* Floyd-Warshall uses one distance matrix and one predecessor matrix, both updated in place, and each predecessor row can be used directly, without copying, as the shortest-path tree from that vertex.

Bellman-Ford toward a target is an ordinary single-source pass over a distinct `reversed_graph` type, so passing the unreversed graph does not compile. Its result type (`target_paths`, with a `next` pointer) deliberately does not fit the existing path helper, so paths cannot silently come out backwards. Vertices whose distance is undefined get −∞, found by a BFS from the vertices that changed in round n.

Weights are read as text and scaled ×100 into integer-valued doubles, so sums are exact and a zero-weight cycle such as 0.3, −0.1, −0.2 is not reported as negative. A new benchmark program (`benchmark_part3`) prints CSV rows, and a Python harness, a config file and a 32 GB Azure VM produce the numbers for four case studies on five graphs: Bellman-Ford distances from 10, 20 and 30 to 100; Floyd-Warshall distances among {10, 20, 30, 40, 50}; mean times over 10 runs; all-pairs Bellman-Ford against Floyd-Warshall. Repeated timing shares a 600 s budget per step; runs that produce an answer run once, however long; anything that cannot be measured is extrapolated and labelled; anything that does not fit in memory is reported, not run.

**How the existing system works, per this document.** Graphs are typed by compile-time policies (`directed` / `undirected`, `weighted<W>`) over CSR or matrix storage and checked by the concepts `graph_like` and `weighted_graph`. Algorithms are free templates in `gl::algorithms`. BFS, DFS and three Dijkstra versions already follow out-arcs; Dijkstra throws on negative weights. `reconstruct_path` walks a `parent` array of a source-rooted tree (`parent_tree`). `read_edge_list` drops self-loops and, in an unpushed commit, counts the negative ones. The Part 2 benchmark hard-codes `undirected` and runs on Azure through `azure_part2.sh`.

## Paraphrase 2: the implementation plan (lines 629 to 825)

Fifteen atomic commits on `feature/part3`, each leaving `make test` passing with no new warnings: (1) ignore the input data and add the design documents; (2) turn the negative-self-loop counter into a vector of loop edges; (3) a weight-parser hook in `read_edge_list`; (4) the generic `fixed_point_weight` parser; (5) `reversed_graph`; (6) a looser `parent_tree` that accepts spans, and a `reconstruct_path` that stops instead of looping; (7) Bellman-Ford toward a target with both optimizations; (8) the whole-graph negative-cycle check; (9) Bellman-Ford differential tests (Dijkstra, graphs built from potentials, brute force on tiny graphs); (10) Floyd-Warshall with hand and differential tests and the zero-cycle regression fixture; (11) the benchmark program and Makefile targets; (12) the harness, config and harness tests; (13) the Azure script and the report-table script; (14) documentation; (15) the case-study results after an owner-approved Azure run. Each file entry names its functions, error messages and exact hand-computed test values. Verification: a build without warnings, `make test` on macOS and later on Linux on the VM, `make test-part3`, negative tests shown to fail with their guard removed, an owner-approved calibration, and an acceptance list of the rows each CSV must contain.

## Findings

### Major

* **M1. What `fw` mode prints when the graph has a negative cycle is not defined.** Section 7 (lines 398 to 401), Section 8 `fw` (line 421), CUJ 2 (lines 77 to 79), Section 9 `negative_cycle` (line 441), Acceptance (line 825). With a negative cycle "every distance and predecessor except the witness is unspecified, and `tree_from` asserts", but the assertion is compiled out in the `-DNDEBUG` release build. Floyd-Warshall never produces −∞, so the `negative_cycle` status ("distance −inf") does not describe its output. Whether W_1 or W_2 has a negative cycle is not stated, so this may well happen in case study 2. **Fix:** state the `fw` behaviour when `negative_cycle()` is true (for example: the `cycle` row, the 20 `path` rows with status `negative_cycle` and no distance or path, `tree_from` never called) and extend the `negative_cycle` status to Floyd-Warshall.
* **M2. `extrapolated` and `fewer_runs` overlap, and the 10-run Floyd-Warshall mean has no stated origin.** Section 9 (lines 442, 446), Goal 8 (line 47), CUJ 2 (line 79), Section 8 `fw` / `calibrate` (lines 421, 424). The table defines `extrapolated` as "a statistic computed from fewer runs than asked", which also describes `fewer_runs`; Goal 8 uses `extrapolated` only when the first run alone exceeds the budget. It is not said whether the mean is c·n³ or the single run, nor which process computes it (the binary's `estimate` row or the harness); in `fw` mode the binary has no calibration data, which comes from a separate `calibrate` launch. **Fix:** redefine `extrapolated` as "not measured: derived from a model (formula in the note)", state the formula per case (Floyd-Warshall mean = c·n³ from that graph's calibration; all-pairs = n × mean pass time) and which component combines calibration output with the step's rows.
* **M3. Floyd-Warshall on W_3 to W_5 gets three different statuses.** Non-Goals (line 54, "reported as skipped"), CUJ 3 (line 85, "`no_memory` (or `skipped` for time)"), Section 9 (`skipped` = "a step turned off in the config"), config entry (line 715, `run_fw=no`, "reported `no_memory` by the harness check anyway"). **Fix:** one precedence rule (for example, the memory check first, so W_3 to W_5 give `no_memory`; `skipped` only for config-disabled steps that would fit), and Non-Goals worded to match.
* **M4. The per-launch timeout is never given, and it could kill the hours-long answer runs.** Section 10 ("one timeout per launch", line 455), Goal 8 ("run once, however long they take"), CUJ 2. The two Floyd-Warshall answer runs are estimated at 1.5 to 8 h each; the timeout's value, how it is set and how it relates to the calibrated estimate are not stated. **Fix:** the timeout rule per mode (a multiple of the calibrated estimate, or none for answer runs) and where it is configured.
* **M5. "Step", the unit of the time budget, is never defined.** Goal 8; Section 8 (`--budget-seconds` "per repeated step", variants "with its own budget"); CUJs 4 and 6. It could be one launch, one algorithm in a launch, or one optimization variant, and Section 8 implies different answers in different places; mean, sample count and status all depend on it. **Fix:** a glossary entry, for example: "Step: one timed quantity in one launch (graph, mode, algorithm or variant); its repeated runs share one budget; the `reverse` and `bellman_ford_pass` rows of a `bf` run belong to the same step."
* **M6. Nothing owns the cross-check behind `mismatch`.** Section 9 `mismatch` (line 445), Alternative U (line 610), Section 8 modes, Acceptance ("no `mismatch`"). No mode is described as running Bellman-Ford toward each vertex of the set: `fw` lists only `floyd_warshall(g)` and `bf` uses one target. It is not said whether the binary or the harness compares, or in which run. **Fix:** for example, "`fw` also runs one untimed `bellman_ford_on_reversed` toward each vertex of `--set` and marks a `path` row `mismatch` on any inexact difference."
* **M7. The two edge types are not shown to be compatible.** Section 2 (line 181) and the signatures of Sections 4, 5 and 7. `edge_list` stores `std::vector<input_edge_t<W>>`, the algorithms take `std::span<const weighted_edge<weight_type>>`, and "the program passes the list through"; neither type is defined in the document. **Fix:** state that `input_edge_t<weighted<X>>` is `weighted_edge<X>` (or describe the conversion).

### Nits

* **N2. Graph sizes are only implied.** The memory figures imply n = 100,000, 1,000,000 and 10,000,000 for W_3 to W_5; edge counts are never given, though the time estimates depend on them. Add a table of n, m and negative arcs per graph.
* **N3. Case studies are referred to by number but never numbered.** Alternatives F, T and U say "case study 1/2"; Goal 6 lists them without numbers. Number them in Goal 6.
* **N4. Alternative F's cost contradicts Section 8.** "3 × 10 times in case study 1" against "one run answers every source" (10 passes, not 30). Correct the count.
* **N5. The Floyd-Warshall side of the all-pairs comparison on W_3 to W_5 is unstated.** CUJ 4 says only that it "uses its measured single run where one exists". State what is reported there (a c·n³ estimate with its memory caveat, or nothing).
* **N6. Calibration decides twice.** CUJ 6 says calibration "decides which timings are repeated and which are extrapolated"; Section 8 has each mode decide at run time by the budget rule. Say that calibration only estimates and the run-time rule decides (or the reverse).
* **N7. The Azure workflow assumes `azure_part2.sh` is known.** Section 10 and plan item 14 name `create`, `setup`, `calibrate`, `start`, `fetch` and an "existing auto-shutdown" without their order or meaning, or when the VM is deleted. List the sequence end to end, including `delete`.

* **N9. Some test descriptions omit what a reader needs to check them.** The undirected example (line 758) lists a fourth distance `inf` without saying n = 4 with vertex 4 isolated; "statement example" presumably means the assignment's example. State n and name the source.
